Pass configuration to a sandbox with plain environment variables, Kubernetes
`Secret` references, and labels.

## Environment variables

```yaml
spec:
  env:
    - name: LOG_LEVEL
      value: debug
```

## Secrets

Secrets are ordinary Kubernetes `Secret`s that you reference from the sandbox.

**First, create the Secret** in the same namespace as the sandbox:

```bash
kubectl create secret generic my-secret --from-literal=api-key=sk-1234567890
```

**Then reference it** from the sandbox, one entry per environment variable:

```yaml
spec:
  secrets:
    - env: API_KEY
      valueFrom:
        secretKeyRef:
          name: my-secret        # the Secret's name
          key: api-key           # the key within that Secret
      allowedHosts: ["api.example.com"]
```

Inside the guest, `API_KEY` holds a placeholder, not the real value. The real value
is substituted only into outbound requests to the hosts in `allowedHosts`, so a
leaked env dump or log line never exposes the credential.

### Fields

| Field | Required | Description |
|---|---|---|
| `env` | yes | The environment variable name the guest sees. |
| `valueFrom.secretKeyRef.name` | yes | Name of a `Secret` in the sandbox's namespace. |
| `valueFrom.secretKeyRef.key` | yes | The key within that `Secret`. |
| `allowedHosts` | no | Hosts the real value may be substituted into. Empty means it is never substituted anywhere. |

`allowedHosts` accepts exact hosts (`api.example.com`) and suffix wildcards
(`*.example.com`).

<Note>
  Secrets are read once at boot. Changing the referenced `Secret` does not affect a
  running sandbox; recreate it to pick up the new value.
</Note>

<Warning>
  The Secret must exist in the sandbox's namespace before the sandbox starts. A
  missing Secret keeps the sandbox from booting.
</Warning>

## Labels

Labels on the `Sandbox` are copied to its Pod and Service, so you can select
sandboxes the usual way:

```yaml
metadata:
  labels:
    team: payments
    env: staging
```

```bash
kubectl get sandbox -l team=payments
```
